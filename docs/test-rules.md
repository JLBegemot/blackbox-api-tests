# Правила чёрноящичных API-тестов

Единственный источник правил для тестов под `tests/`. На него опираются
скилл `/api-tests` и агент `test-reviewer`; дублировать эти правила
в скиллах и агентах запрещено — расходятся на первой же правке.

У каждого правила есть идентификатор. Ревью ссылается на идентификатор,
а не пересказывает правило своими словами.

**Главное отличие от белого ящика:** тест — это HTTP-клиент к стенду, поднятому
снаружи. Приложение не собирается, моков нет, БД недоступна.
Обвязка живёт в [`tests/conftest.py`](../tests/conftest.py) — прочитай его
до написания теста.

---

## STAND — стенд и его конфигурация

| ID        | Правило |
|-----------|---|
| STAND-001 | Стенд поднимается **снаружи и вне этого репозитория**, до прогона. Ни тест, ни фикстура, ни скрипт набора не запускают приложение, не управляют контейнерами и не предполагают, в каком порядке стенд стартовал. Адрес стенда — `STAND_URL` (по умолчанию `http://localhost:8000`); за его готовностью к моменту прогона следит тот, кто стенд поднимает. |
| STAND-002 | Кейс «поведение при другом значении флага» требует второго профиля стенда и отдельного прогона. В общий набор такие кейсы не берутся; в плане они получают ✖ с пометкой «нужен второй профиль». |
| STAND-003 | Почтового приёмника на стенде нет, `EMAIL_VERIFICATION_ENABLED=false`. Кейс, которому нужно письмо (happy path верификации и сброса пароля), помечается ⚠️ в карте покрытия и в код не идёт. |


## STRUCT — расположение и именование

| ID | Правило |
|---|---|
| STRUCT-001 | Тесты лежат в `tests/`, раскладка по областям фич: `tests/<область>/`. Каталог области заводится, когда в него появляется первый тест; сейчас существуют `tests/auth/` и `tests/user/`. Существующий список каталогов — факт файловой системы, а не список из документации. |
| STRUCT-002 | Файл — на фичу, а не на роутер: `tests/<область>/test_<feature>.py`. Новый файл заводится, только если фичи в существующих действительно нет. |
| STRUCT-003 | Имя теста описывает поведение, а не вызов: `test_reset_confirm_rejects_unknown_token`, а не `test_post_confirm_2`. |
| STRUCT-004 | Пояснительный докстринг в начале тест-**файла** не пишется: что проверяет тест, говорят его имя (STRUCT-003) и маркер (MARK-001). Докстринг у самой тест-функции разрешён и полезен там, где сценарий неочевиден. |
| STRUCT-005 | Регрессионный тест на исправленный баг обязателен и называется по багу. |

## MARK — маркеры контракта

| ID | Правило |
|---|---|
| MARK-001 | Каждый тест несёт `@pytest.mark.endpoint("METHOD /path")` с операцией из контракта. На коллекции `conftest.py` сверяет её со спекой (live со стенда, офлайн — снапшот `contracts/openapi.json`); незнакомая операция роняет коллекцию. Новая ручка → сначала `uv run python scripts/openapi_snapshot.py --dump`. |

## FIXT — фикстуры и обвязка

| ID | Правило |
|---|---|
| FIXT-001 | Обвязка берётся из `tests/conftest.py`. Собственный `httpx.AsyncClient`, свой register-хелпер, свой разбор SSE в тест-файле — **запрещены**. |
| FIXT-002 | Фикстуры не собирают приложение — они ходят по HTTP: `client_ip` (уникальный IP на тест), `api` (клиент с этим `X-Forwarded-For`), `register_user` (фабрика: регистрирует нового пользователя и возвращает его), `user` (один такой пользователь на тест), `auth` (заголовок), `seed_resume` (резюме через `POST /api/v1/resumes/upload`), `poll_until` (опрос с дедлайном), `sse` (чтение потока с дедлайном). |
| FIXT-003 | Тест-файл добавляет только **сидинг своих данных**, и только через API. |
| FIXT-004 | Фикстуры не убирают за собой **серверные данные**: изоляцию даёт уникальность, а не очистка. Освобождать собственные клиентские ресурсы (закрыть `httpx.AsyncClient`) — можно и нужно; ходить после теста в API, чтобы «прибраться», — нельзя. |

## DB — граница чёрного ящика

| ID | Правило |
|---|---|
| DB-001 | Прямой доступ к БД / Redis / S3 из теста **запрещён** — тесту доступен только HTTP-интерфейс API. `docker exec`, `kubectl exec` и прочий доступ к внутренностям стенда — то же нарушение, даже если технически порт открыт. |
| DB-002 | Изоляция данных — свой пользователь `t-{uuid}@example.com` на тест (фикстура `user`; домен `.test` не годится — email-validator бэкенда режет special-use TLD). База между тестами не чистится; набор обязан оставаться параллелизуемым (`uv run pytest -n auto`, плагин `pytest-xdist` в dev-группе) и пригодным для прогона против общего dev-стенда. |
| DB-003 | Побочный эффект проверяется той ручкой, которая его отдаёт (запись — через GET, удаление — через 401/404 после). Если никакая ручка эффект не отдаёт (пример: `ip_address` в audit-log) — это ⚠️ в карте покрытия, а не тест с косвенным ассертом. |

## AUTH — авторизация

| ID | Правило |
|---|---|
| AUTH-001 | У каждой закрытой ручки есть happy path и **отказ авторизации** (запрос без заголовка). Плюс **отказ валидации** — если у ручки есть тело или параметры, которые можно нарушить; у ручки без входных данных этой категории нет, и её отсутствие не находка. |
| AUTH-002 | Тест «чужой объект» обязателен для всего, что адресуется по id. Ожидание — **404, а не 403**: существование чужой сущности не раскрывается. Второй пользователь берётся фабрикой `register_user` из `tests/conftest.py` — свой register-хелпер в тест-файле по-прежнему запрещён (FIXT-001). |
| AUTH-003 | Невалидный UUID в пути — тоже 404, а не 422. |
| AUTH-004 | Токен добывается **регистрацией** (фикстуры `user` / `register_user`): при выключенной верификации register сразу возвращает JWT. Отдельный логин — только там, где логин и есть предмет теста. `create_access_token` недоступен — подписать токен вне бэкенда нельзя, и не надо. |

## RATE — изоляция клиента

| ID | Правило |
|---|---|
| RATE-001 | Каждый тест ходит со своим `X-Forwarded-For` — его даёт фикстура `api`. Стенд пишет клиентский адрес в серверное состояние (журналы, счётчики), и уникальный IP не даёт параллельным тестам связываться через него. Ждать сброса какого-либо окна `sleep`-ом запрещено в любом случае (FORBID-002). |
| RATE-002 | Состояние, привязанное к пользователю, изолируется уникальным пользователем на тест — не общим аккаунтом. |

## JOB — фоновые задачи

| ID | Правило |
|---|---|
| JOB-001 | Результат фоновой задачи ждётся только фикстурой `poll_until` — с дедлайном. Свой цикл опроса и любое ожидание без дедлайна запрещены (FIXT-001, FORBID-002). |
| JOB-002 | `status` в немедленном ответе точным значением не пинуется: worker реальный, между ответом и проверкой — гонка. Ассерт делается множеством допустимых значений (`{"queued", "running", "done"}`). |
| JOB-003 | `progress` и `updated_at` в промежуточных ответах точными значениями не пинуются: проверяются тип, диапазон и монотонность, а не конкретное число. |

## SSE — потоки событий

| ID | Правило |
|---|---|
| SSE-001 | Первый кадр потока — снапшот текущего состояния: подписчик получает статус сразу, не дожидаясь следующего события. |
| SSE-002 | Поздний подписчик (задание уже терминальное) получает терминальный кадр первым, и поток закрывается сразу. |
| SSE-003 | Полный цикл проверяется последовательностью статусов и **фактом закрытия потока**, а не только наличием событий. |
| SSE-004 | `progress` по потоку не убывает и заканчивается терминальным значением; промежуточные значения точными числами не пинуются (JOB-003). |
| SSE-005 | `text/event-stream` читается **только** фикстурой `sse` — в ней дедлайн и лимит событий. Свой разбор потока в тест-файле запрещён (FIXT-001), бесконечное чтение запрещено (FORBID-002). |

## ASSERT — ассерты

| ID | Правило |
|---|---|
| ASSERT-001 | **Ассерт на суть требования, а не только на статус-код.** Тест, который проверяет 200 и не смотрит в тело, требование не проверяет. |
| ASSERT-002 | В ассерт статуса кладётся тело: `assert resp.status_code == 200, resp.text`. Без этого падение в CI нечитаемо. |
| ASSERT-003 | Проверяются значимые поля ответа, а не факт их наличия: значение `Location`, диапазон `scores`, `model_used == "heuristic"`. |
| ASSERT-004 | Негативный кейс обязан быть осмысленным: тест должен падать по **той** причине, которую проверяет. Классическая ловушка — 422 на схеме вместо ветки хендлера (токен короче 16 символов не дойдёт до проверки токена). |
| ASSERT-005 | Ассерт на полный JSON-дамп ответа запрещён: ломается от любого нового поля и ничего не сообщает о требовании. |
| ASSERT-006 | Тексты, сформированные агентом (даже эвристикой), дословно не пинуются: проверяются структура, границы, инварианты. |

## RED — красный тест

| ID | Правило |
|---|---|
| RED-001 | Красный тест — всегда вопрос «дефект сервиса или неверная предпосылка теста», и решает его **пользователь**. Ни агент, ни пайплайн не выбирают ответ за него. |
| RED-002 | Неверная предпосылка — правится тест. Подгонка ассерта под фактический ответ **без** ответа на вопрос RED-001 — то же самое, что «позеленить», и запрещена (FORBID-010). |
| RED-003 | Пользователь подтвердил дефект сервиса — тест остаётся красным по сути и помечается `@pytest.mark.xfail(reason="<дефект>, <ссылка на задачу>", strict=True)`. Такой тест **отгружается**: `strict=True` уронит набор, когда дефект починят, и пометка снимется вместе с ним. Молча удалять, скипать или ослаблять такой тест запрещено. |

## FORBID — сводка запретов

| ID | Запрещено | Почему |
|---|---|---|
| FORBID-001 | Импорт любого модуля бэкенда — то есть любой импорт вне стандартной библиотеки и dev-группы `pyproject.toml` — и установка бэкенда в окружение тестов | весь смысл чёрного ящика; версия бэкенда не пинуется |
| FORBID-002 | `time.sleep` и любые ожидания без дедлайна | тест виснет в CI |
| FORBID-003 | Прямой доступ к БД / Redis / S3 / внутренностям стенда | DB-001 |
| FORBID-004 | Зависимость от порядка тестов и общие данные между ними | DB-002 |
| FORBID-005 | Тавтология вроде `assert 200 == 200` и тест без единого ассерта | тест не может упасть |
| FORBID-006 | Ассерт на полный JSON-дамп ответа | ASSERT-005 |
| FORBID-007 | Хардкод данных чужих окружений: настоящие e-mail, ключи, id из прода | утечка и нестабильность |
| FORBID-008 | Секреты и ключи в коде теста | окружение задаёт стенд |
| FORBID-009 | Дубль теста вместо правки существующего, когда сценарий уже поднят | правится существующий тест |
| FORBID-010 | «Позеленить» тест правкой бэкенда, конфигурации стенда или подгонкой ассерта | прод-код в другом репозитории — физически нельзя; «подкрутить стенд, чтобы позеленело» — то же нарушение. Что делать вместо этого — RED-001…RED-003 |
| FORBID-011 | Пайплайн `/api-tests` пишет **только** под `tests/`, `plans/`, `docs/` и `.claude/tmp/`. Конфигурация стенда, `scripts/` и `contracts/` им не правятся; снапшот `contracts/openapi.json` обновляется отдельным осознанным действием (`openapi_snapshot.py --dump`), и его дифф в MR с тестами либо согласован явно, либо вынесен | снапшот — опора гейта MARK-001 и валидатора кейсов; молчаливая правка обесценивает обе проверки |

## Как проверить себя перед ревью

Стенд к этому моменту уже поднят снаружи и готов (STAND-001).

```bash
uv run pytest -q
uv run python scripts/openapi_snapshot.py --check   # live-спека не разошлась со снапшотом
```
