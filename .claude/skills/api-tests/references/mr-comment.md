# Описание MR к написанным тестам

Цель: ревьюер видит, **на какие ручки** написаны тесты и **какие сценарии** они
покрывают — не поднимая переписку с автором и не читая контракт.

Готовится всегда, даже если MR ещё не создан: платформа — SourceCraft, CLI для создания
MR в системе нет, поэтому `/ship` пушит ветку и печатает готовый текст, а MR создаёт
человек.

---

## Что обязательно содержит

1. **Ручки** — идентификаторы как в контракте: `GET /api/user/personal-data`.
2. **Режим проектирования** — `full` (вся ручка) или `delta` (только изменение).
3. **Ссылка на тест-план** — `plans/<id>-test-plan.md`, он в том же диффе.
   Источником была Linear-задача — рядом строка **Задача** со ссылкой на неё.
4. **Сценарии, которые фактически реализованы** — по строке на тест.
5. **Идентификатор теста** — `tests/user/test_profile.py::test_name`. Это то, что
   ревьюер скопирует в `pytest`, чтобы прогнать один тест.

## Только фактически реализованное

В описание попадает то, что есть в диффе, — не тест-план целиком. План по ходу написания
меняется: кейсы объединяются в `parametrize`, разбиваются, отпадают как дубли, добавляются
новые. План, приложенный как есть, начинает врать про содержимое MR.

Отсюда:

- **Кейсы, которые не были написаны, в описание не включать** — ни строкой «не написан»,
  ни счётчиком «N из M кейсов плана». Что не реализовано — сказать пользователю в финальном
  отчёте: это разговор с автором, а не с ревьюером.
- **Сценарий описывать так, как он реализован в коде**, а не как он был сформулирован
  в плане.
- **Идентификатор строки — путь к тесту из кода, а не `TC-NNN` из плана.** Номера кейсов
  к моменту MR уже не совпадают с тестами.
- `⏳`- и `✖`-кейсы в диффе не лежат вовсе (они живут только в плане) — в таблицу
  не попадают.
- Тест, помеченный `@pytest.mark.xfail(strict=True)` по подтверждённому дефекту
  сервиса (RED-003), — **реализованное**: он в диффе и должен быть в таблице
  с пометкой `⚠️ xfail` и ссылкой на задачу дефекта. Ревьюер обязан понимать,
  почему в наборе есть заведомо падающая проверка.

## Доработанные существующие тесты

Правка существующего теста — тоже содержимое MR: в диффе есть изменённая функция,
и ревьюеру нужно понимать, что там появилась новая проверка, а не переформатирование.

Такие тесты идут строкой в той же таблице с пометкой `➕ дополнен`; в колонке «Сценарий» —
**что именно добавлено**, а не весь смысл теста заново.

В итоговой строке считать отдельно: `3 новых + 2 дополненных + 1 xfail`. Смешивать
доработки с новыми в одном счётчике нельзя — по нему судят об объёме MR.

## Шаблон

````markdown
## Автотесты: <ручка или фича>

| | |
|---|---|
| **Ручки** | `GET /api/user/me`, `GET /api/user/personal-data` |
| **Профиль** | `http` |
| **Режим проектирования** | delta (только изменение) |
| **Тест-план** | `plans/CUS-6-test-plan.md` |
| **Задача** | [ABC-123](https://linear.app/team/issue/ABC-123) — если источником была Linear-задача |

### Реализованные сценарии

| Сценарий | Тип | Вид | Тест |
|---|---|---|---|
| Ручка отдаёт данные текущего пользователя | Positive | ✅ новый | `tests/user/test_profile.py::test_me_returns_current_user` |
| Запрос без токена отклоняется | Negative | ✅ новый | `tests/user/test_profile.py::test_me_without_token_is_rejected` |
| Добавлен ассерт на `consent_given_at` в экспорте | Positive | ➕ дополнен | `tests/user/test_personal_data.py::test_personal_data_export_returns_user_data` |
| Небулев `confirm` — 422 (дефект: отвечает 500, [ABC-124](…)) | Negative | ⚠️ xfail | `tests/user/test_account_deletion.py::test_revoke_consent_rejects_non_boolean_confirm` |

### Проверки

- `uv run pytest -q` — <N> passed, <M> xfailed
- `uv run python scripts/openapi_snapshot.py --check` — снапшот совпадает

**Итого:** 2 новых теста + 1 дополненный + 1 xfail.
````

## Правила оформления

- Ручки — точно как в `contracts/openapi.json`, с плейсхолдерами пути.
- Снапшот контракта обновлён (`--dump`) — сказать об этом отдельной строкой: ревьюер
  увидит `contracts/openapi.json` в диффе и должен понимать, почему он там.
- Ничего не выдумывать: не было прогона — не писать его результат.
