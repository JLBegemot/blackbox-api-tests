# API Tests — Playbook (чёрный ящик)

Цель: по ручке или задаче построить структурированный тест-план,
а после согласования — написать тесты.

Транспорт один (REST поверх FastAPI), поэтому ось разбиения здесь не транспорт,
а **профиль ручки** — см. [`profiles.md`](profiles.md). Заголовки шагов ниже
и разделы в `profiles.md` совпадают: читать вместе, а не по очереди.

Правила написания тестов — в [`docs/test-rules.md`](../../../../docs/test-rules.md).
Этот файл про **процесс**, тот — про **код**. Не дублировать.

Прод-код бэкенда живёт в отдельном репозитории; путь к его чекауту — переменная
`BACKEND_REPO`. При проектировании он — **справочный источник** (коды ошибок,
формулы, ветки), но тесты и обвязка его не касаются: ни импортов, ни правок.
Переменная пуста или путь не существует — чекаута нет, и каждый шаг ниже,
где он упомянут, идёт по своей запасной ветке: известен PR бэкенда — его дифф
и файлы через GitHub MCP (равноценно чекауту, см. «Источники из MCP» в SKILL.md);
иначе пробный запрос к стенду с пометкой `[инференс]`.

## Шаг 0 — Определить режим

| Режим | Когда | Скоуп кейсов |
|---|---|---|
| `full` | Ручки нет в наборе: нет в `contracts/openapi.json`, нет тестов | Вся ручка целиком |
| `delta` | Ручка уже есть, задача — покрыть изменение или закрыть пробелы | **Только изменение** |

### Режим определяется по фактам репозитория, а не по формулировке задачи

Формулировка человека — гипотеза, репозиторий — факт. «Новая ручка» регулярно означает
«ручка давно в контракте и покрыта пятнадцатью тестами»: задача переоткрыта, ТЗ скопировано
из старого, автор помнит проект, а не репозиторий.

Поэтому **до** выбора режима проверить две вещи:

```bash
# 1. Есть ли ручка в контракте
jq -r '.paths | keys[]' contracts/openapi.json | grep -i '<фрагмент пути>'

# 2. Есть ли тесты на эту ручку
grep -rn '"/api[^"]*<фрагмент>' tests/
```

Всё пусто → `full`. Есть хоть что-то → `delta`, и сказать прямо, что найдено:

> Ручка не новая: есть в контракте (`contracts/openapi.json`) и покрыта `<N>` тестами
> (`tests/<область>/test_<feature>.py`). Предлагаю режим `delta` — покрыть изменение.
> Нужен `full` (пересмотр целиком) — скажи, пересоберу план.

### Режим `delta` — что нужно на входе

| Вход | Обязательность | Зачем |
|---|---|---|
| **План, Linear-задача** или описание изменения | обязательно | формулы, единицы, границы, out of scope |
| **Дифф ветки бэкенда** (`git -C "$BACKEND_REPO" diff main...<ветка>`; чекаута нет, но есть PR — дифф PR через GitHub MCP → `.claude/tmp/<id>/backend.diff`, равноценно) | обязательно, если есть чекаут и ветка либо PR | имя поля, тип, дефолт, где потребляется, где валидируется |
| **Актуальная спека из PR** (`docs/openapi.json` из ветки бэкенда → `.claude/tmp/<id>/openapi.json`, см. Шаг 1) | обязательно, если есть ветка или PR | что реально поменялось в схемах и путях (дельта — Шаг 1а) |
| **Описание изменения словами** | если нет ни плана/задачи, ни ветки/PR, ни дельты | иначе дельту не определить — остановиться и попросить |

**Ручка на входе может быть не названа** — список ручек выводится из плана и диффа.

### Одно изменение — несколько ручек

Изменение общей Pydantic-схемы, общей зависимости (`get_current_user`,
`rate_limit_dep`) или общего SSE-итератора проявляется сразу в нескольких ручках.
Все они входят в дельту, даже если в заголовке задачи названа одна.

1. Собрать полный список ручек, где изменение видно — по диффу и дельте контракта.
2. Показать список пользователю **до** проектирования кейсов: берём все или сужаем.
3. В плане группировать кейсы по ручкам, размещение указывать по файлам.

**В режиме `delta` кейсы проектируются только на изменённую часть.** Пробелы
в существующем поведении — отдельным списком «Дополнительно не покрыто», в план
без явного согласия не включать.

## Шаг 0б — Прочитать источник требований

Из источника вытащить то, чего контракт не содержит: формулы, единицы, границы
и лимиты, требования согласованности, out of scope, поведение SSE.

**Out of scope читать так же внимательно, как scope.**

### Приоритет источников

| # | Источник | Что даёт | Чему верить при конфликте |
|---|---|---|---|
| 1 | **Наблюдаемое поведение стенда** | как оно работает на самом деле | всегда право |
| 2 | **Код хендлера** (чекаут `$BACKEND_REPO` или дифф/файлы PR через GitHub MCP, справочно) | фактические коды ошибок, ветки | прав против контракта и плана |
| 3 | **Контракт** (спека из PR `.claude/tmp/<id>/openapi.json` — для изменений задачи; снапшот `contracts/openapi.json` — для устоявшегося) | что сервис обещает | прав против плана |
| 4 | **Существующие тесты** | что уже считалось верным | не доказательство требования |
| 5 | **Текст плана / Linear-задачи** | зачем это сделано, out of scope | самое общее |

Каждое расхождение — находка: тест пишется по фактическому поведению,
а расхождение выносится пользователю.

**Коды ошибок в контракте неполные.** FastAPI кладёт в OpenAPI только объявленные
`responses`; фактические 400/403/404/409/503 живут в теле хендлера. Прочитать хендлер
в чекауте бэкенда — обязательный шаг; чекаута нет, но известен PR — посмотреть файл
хендлера через `mcp__github__get_file_contents`; и этого нет — проверить пробным
запросом к стенду и пометить `[инференс]`.

### Условие срабатывания не выдумывать

У кейса на ошибку с неизвестным триггером ровно два законных исхода:

1. Пользователь ответил, чем ошибка триггерится → обычный исполняемый кейс.
2. Ответа нет → кейс **в плане** со статусом `⏳` и пометкой «триггер неизвестен».

Третьего нет. **Выбрасывать такой кейс из плана запрещено.**

### Граница между ⏳ и ✖ — один вопрос

> Сможет ли человек выполнить этот кейс руками, когда появятся данные или условие?

| Ответ | Статус | Что делает писатель |
|---|---|---|
| Да — не хватает данных, доступа или знания условия | `⏳` | строка в плане + `@pytest.mark.skip(reason=…)`-заготовка |
| Нет и не сможет никогда | `✖` | ничего: только строка в плане |

**Недостижимость через чёрный ящик — это ✖, а не ⏳.** Типичные ✖ здесь:

- нужен почтовый ящик (happy path верификации/сброса) — STAND-005, помечается ⚠️/✖;
- нужно другое значение флага из `.env.stand` — STAND-003 («нужен второй профиль»);
- поломка внешнего сервиса, которую снаружи не воспроизвести;
- гонка внутри arq-воркера, не наблюдаемая через API.

**✖ — не повод убрать кейс из плана.** Он не идёт в код, но остаётся строкой.

## Шаг 1 — Найти контракт и разобрать ручку

Контракт — live-спека стенда, версионированная снапшотом `contracts/openapi.json`.

```bash
# схема одной ручки, не читая весь файл
jq '.paths["/api/v1/ai/tailor"]' contracts/openapi.json

# схема тела запроса
jq '.components.schemas.TailorRequest' contracts/openapi.json
```

**Актуальная спека для проектирования берётся из PR бэкенда — стенд не нужен.**
Бэкенд коммитит спеку в `docs/openapi.json`; забрать её из ветки задачи
в `.claude/tmp/<id>/openapi.json`:

```bash
# есть чекаут бэкенда
git -C "$BACKEND_REPO" show <ветка>:docs/openapi.json > .claude/tmp/<id>/openapi.json
```

Чекаута нет — `mcp__github__get_file_contents` (`path: docs/openapi.json`,
`ref: <ветка PR>`) → тот же файл. Нет ни ветки, ни PR — проектировать по снапшоту
`contracts/openapi.json` как есть, а известные из требований изменения помечать
`[план]`.

Изменения этой задачи искать в спеке из PR, устоявшееся поведение — в снапшоте.
Сверка снапшота с live-спекой стенда (`openapi_snapshot.py --check`) уходит
на шаг генерации (шаг 5 SKILL.md) — там стенд нужен в любом случае;
проектирование он не блокирует.

**Ручки за feature-флагом.** Стенд поднят с `FEATURE_MFA=true` (см. `stand/.env.stand`),
поэтому `/api/v1/auth/mfa/*` смонтированы и есть в live-спеке. Ручка за флагом,
которого нет в `.env.stand`, — это кейс со статусом ✖ «нужен второй профиль» (STAND-003).

## Шаг 1а — Дельта контракта (только режим `delta`)

Дельта — разница между снапшотом и спекой из PR (скачана на Шаге 1),
стенд поднимать не нужно:

```bash
diff <(jq -S . contracts/openapi.json) <(jq -S . .claude/tmp/<id>/openapi.json)
```

Дифф показать пользователю таблицей — это и есть определение дельты:

| Изменение | Минимум кейсов |
|---|---|
| Новое обязательное поле запроса | happy path с полем + 422 без поля |
| Новое опциональное поле | happy path с полем + happy path без него (дефолт) |
| Новое поле ответа | ассерт на значение в happy path, не на наличие |
| Новый код ответа | негативный кейс, воспроизводящий ровно эту ветку |
| Сменился тип поля | ассерт на тип и формат в существующем тесте |
| Новая ручка | полный набор по профилю (`profiles.md`) |

## Шаг 1б — Выявить пробелы в семантике

Контракт описывает **структуру**, но не **бизнес-семантику**. Типичные пробелы:

| Пробел | Где закрывается |
|---|---|
| Фактические коды ошибок | хендлер в чекауте бэкенда; нет чекаута — файл хендлера из PR (GitHub MCP); нет и PR — пробный запрос к стенду |
| Последовательность статусов задания | наблюдение через `poll_until` / SSE |
| Формулы и пороги эвристик | `agents/*_agent.py` в чекауте (справочно) |
| Размеры бакетов rate limit | `stand/.env.stand`; чего там нет — зафиксировать сначала там (отдельным MR) |
| Допустимые значения enum | схема в контракте |

Сначала закрывать пробел самостоятельно, потом спрашивать. Значения искать по месту
использования, не по угаданному префиксу; найденный список объявлять неполным;
инференс помечать `[инференс]`.

## Шаг 2 — Инфраструктура вызова

Обвязка — фикстуры из `tests/conftest.py`. Своей обвязки тест не заводит (FIXT-001).

| Что нужно | Фикстура |
|---|---|
| HTTP-клиент на стенд, уникальный `X-Forwarded-For` | `api` |
| Свежий пользователь (email, password, id, token) | `user` |
| Заголовок авторизации | `auth` |
| Резюме с первой версией | `seed_resume` (через `POST /api/v1/resumes`) |
| Ожидание фоновой задачи | `poll_until` (дедлайн обязателен) |
| Чтение SSE-потока | `sse` (дедлайн обязателен) |

Чего в conftest нет — **зафиксировать в плане как требование к инфраструктуре**
и продолжить. Новая общая фикстура — правка `tests/conftest.py`, она идёт
в гейт Шага 6б: conftest трогают все тесты.

## Шаг 3 — Проверить ручку в контракте

```bash
jq -r '.paths | to_entries[] | .key as $p | .value | keys[] | ascii_upcase + " " + $p' \
  contracts/openapi.json | sort | grep -i tailor
```

Ручки нет в снапшоте — два случая:

**А. Ручка есть в спеке из PR** (`.claude/tmp/<id>/openapi.json`) — это новая ручка
задачи. Проектировать по спеке из PR; снапшот синхронизируется со стендом
на шаге генерации (`openapi_snapshot.py --dump`).

**Б. Ручки нет и в спеке из PR** — это, возможно, задача на разработку бэкенда,
а не на тесты. Сказать прямо, не проектировать кейсы на несуществующую ручку.

**В `cases.yaml` ручка записывается ровно строкой из контракта**, с плейсхолдерами
(`/api/v1/ai/tailor/{job_id}`) — `validate_cases.py` сверяет её со снапшотом;
для новых ручек из PR передать спеку явно:
`validate_cases.py … --spec .claude/tmp/<id>/openapi.json`.

## Шаг 4 — Найти и прочитать существующие тесты

Минимум два поиска — каждый находит то, что не находит другой:

```bash
# 1. по строке пути — тесты, которые дёргают ручку
grep -rn '"/api/v1/ai/tailor' tests/

# 2. по сценарию — тесты, поднимающие нужное состояние другим способом
grep -rn 'jd_source\|seed_resume' tests/
```

Каждый найденный файл **прочитать целиком** и понять, что проверяется ассертами,
а не что обещает имя теста. Нашёлся тест, который поднимает сценарий, — это
**правка существующего теста**, а не новый тест.

## Шаг 5 — Определить пробелы

Для каждого сценария из требований — два вопроса, оба обязательны:

1. **Сценарий** — воспроизводит ли какой-нибудь тест это состояние и этот запрос?
2. **Ассерт** — проверяет ли он ровно то, из-за чего сценарий существует?

«Нет» на любой — пробел, кейс идёт в план. По каждому требованию ядра изменения:
есть ли хотя бы один ассерт **на значение**, который упадёт, если требование сломать?

Сценарий воспроизведён, не хватает проверки → **правка существующего теста** (Шаг 8).

## Шаг 6 — Спроектировать тест-кейсы

Включать только пробелы из Шага 5. Обязательные категории на профиль —
в [`profiles.md`](profiles.md); ниже то, что действует всегда.

### Параметризация

`@pytest.mark.parametrize` — когда один сценарий и много входных значений
с одинаковым результатом, либо перебор enum. Разные setup или разные ассерты —
отдельные тесты. В плане: `TC-NNN — <название> [@parametrize: значения]`.

### Дефолт окружения — не требование

Значение, которое задаёт фикстура или дефолт схемы, а не проектируемая ручка, —
не требование. Для таких полей проверять **тип, формат, диапазон**, а не значение:

```
❌ TC-NNN — scores.total == 72
✅ TC-NNN — scores.total: int в диапазоне 0…100
```

### Поля, меняющиеся по ходу флоу

`status`, `progress`, `updated_at` — не пинуются в общей проверке (JOB-002, JOB-003):
worker реальный, гонка вместо проверки. Немедленный ответ POST — ассерт множеством
`{"queued", "running", "done"}`.

### Тексты агентов дословно не пинуются

Даже на эвристическом пути (ASSERT-006). Проверять структуру, границы, инварианты —
и `model_used == "heuristic"` как признак конфигурации стенда (STAND-004).

### Проверка на дублирование (обязательный проход)

Для каждого кейса: **что конкретно упадёт в этом тесте и не упадёт ни в одном
другом?** Нет ответа — удалить кейс.

### Второй проход дедупа: кейсы, проверяемые из одного ответа

Кейсы, проверяемые из одного и того же ответа одного запроса, — один кейс:

```
❌ TC-002 — ответ содержит Location   /   TC-003 — ответ содержит непустой id
✅ TC-002 — 202 с телом AnalyzeAccepted: id — валидный UUID, Location указывает на poll-URL
```

### Формат тест-кейса

```
TC-NNN — <короткое название>
Тип: Positive / Negative
Профиль: http / sse / llm / job / ratelimit
Сценарий: <что делается>
Предусловие: <состояние — пользователь, резюме, версия, состояние задания>
Запрос: <метод, путь, ключевые поля>
Ожидаемый результат: <код + проверяемые поля ответа и наблюдаемые следствия>
Приоритет: blocker / critical / normal
Источник: [код] / [контракт] / [план] / [инференс]
```

## Шаг 6б — Гейт: все решения пользователя одним блоком

Набросав кейсы, собрать **все** вопросы к пользователю. Это блокирующий гейт:
пока ответов нет, финальная таблица кейсов не выводится.

Что попадает в гейт:

| Класс решения | Примеры |
|---|---|
| **Нетривиальные тестовые данные** | состояние задания, которое не поднимается через API; резюме определённой формы |
| **Значения, которых дизайнер не знает** | допустимые значения поля, которых нет ни в схеме, ни в тестах |
| **Правка общего `tests/conftest.py`** | новая фикстура — ею пользуются все тесты |
| **Расширение скоупа** | изменение задело несколько ручек: берём все или сужаем |
| **Второй профиль стенда** | кейс требует другого значения из `.env.stand` — заводим профиль или ✖ |
| **Выбор между двумя предусловиями** | оба рабочие, но у одного есть цена (время, нестабильность) |

**Сначала проверить репозиторий, потом спрашивать.** **Не своё решение в гейт
не тащить** — имена, размещение, способ сборки фикстуры решает писатель по правилам.
**Дописывать вопросы после готового плана запрещено.**

Если пользователь говорит, что сценарий воспроизвести нельзя — кейс идёт в план
со статусом ⏳ с причиной и условием разблокировки.

## Шаг 7 — Определить, где размещать тесты

- **Файл есть** — новые тесты добавляются функциями в существующий файл.
- **Файла нет** — создать по STRUCT-002 в каталоге области (`tests/auth/`, `tests/ai/`, …).
- **Тест-логика принципиально другая** (SSE против poll) — новый файл рядом.
- **Кейсов много** — один файл не должен превышать ~700 строк; делить по логической
  группе, а не по алфавиту.

## Шаг 8 — Сформировать итоговый тест-план

План выводится **таблицами**. Файл: `plans/<id>-test-plan.md`.

```
## Тест-план: <ручка или фича>
```

### Второй артефакт: `cases.yaml`

`.claude/tmp/<id>/cases.yaml` — исполняемое подмножество, уходит в промпт
`test-writer` **путями, а не текстом**.

```yaml
task: 06-sse-stream
plan: plans/06-sse-stream-test-plan.md
spec: contracts/openapi.json
cases:
  - id: TC-001
    endpoint: GET /api/v1/ai/tailor/{job_id}/stream
    profile: sse
    action: new                      # new | edit
    target_file: tests/ai/test_tailor_stream.py
    title: стрим доходит до done с монотонным progress
    precondition: авторизованный пользователь, задание поставлено POST-ручкой
    expect: последовательность queued→running→done, progress не убывает
    priority: blocker                # blocker | critical | normal
    source: код                      # код | контракт | план | инференс
```

Проверить: `uv run python scripts/validate_cases.py .claude/tmp/<id>/cases.yaml`.

`⏳`- и `✖`-кейсы в `cases.yaml` **не попадают** — они живут только в плане.

### Секция «Правки существующих тестов»

**Если сценарий воспроизведён — правим существующий тест, новый не пишем**
(FORBID-009). Формулировать так, чтобы писатель не перечитывал весь файл:
имя теста, что именно добавить, и одной фразой — почему этого не хватает.

## Незыблемые правила

- **Без утверждённого плана код не пишется.** Гейт Шага 6б не пропускается.
- **Правила написания тестов — только из `docs/test-rules.md`.**
- **Режим определяется по фактам репозитория, не по формулировке задачи.**
- **Проектирование по спеке из PR** (`docs/openapi.json` ветки бэкенда) плюс
  снапшот `contracts/openapi.json` — стенд для сбора информации не нужен.
  Live-спека стенда сверяется `--check` перед генерацией (шаг 5 SKILL.md).
- **Коды ошибок — из хендлера (чекаут бэкенда или файлы PR) или пробного запроса**,
  не из объявленных `responses` контракта.
- **Приоритет источников: стенд → код хендлера → контракт → тесты → план.**
- **Пробел меряется и сценарием, и ассертом.**
- **Фича-флаг — свойство стенда.** Кейс «при другом значении флага» — ✖ «нужен
  второй профиль», в общий набор не идёт (STAND-003).
- **Кейс, которому нужно письмо, — ⚠️/✖** (STAND-005). Не выдумывать обходной путь.
- **Кейсы, проверяемые из одного ответа, — один кейс.**
- **Дефолт окружения — не требование.**
- Кейс на ошибку с неизвестным триггером включается в план со статусом ⏳.
- **✖-кейс всё равно остаётся строкой в плане.**
- **Все решения пользователя — одним блоком в гейте, до таблицы кейсов.**
- Сценарий воспроизводим, но ожидание неизвестно → писать с вероятным значением
  и пометкой `❓`, а не блокировать.
