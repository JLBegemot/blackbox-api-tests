# Генерация API-тестов (чёрный ящик)

Оркестратор. Держит весь сценарий, потому что шаг 4 (гейт согласования) требует
диалога с пользователем, а сабагенты не разговаривают.

Тесты в этом репозитории — HTTP к поднятому стенду. Прод-код бэкенда живёт
в отдельном репозитории и здесь **не редактируется никогда**.

**Чекаут бэкенда** — справочный источник, путь берётся из переменной `BACKEND_REPO`.
Переменная пуста или путь не существует — чекаута нет: работать по контракту
и пробным запросам к стенду, помечая выводы `[инференс]`. Проверять так:

```bash
[ -n "$BACKEND_REPO" ] && [ -d "$BACKEND_REPO" ] && echo "чекаут есть: $BACKEND_REPO"
```

**Аргумент** — источник требований, любой из пяти:

| Вход | Как распознать | Что делать |
|---|---|---|
| `plans/NN-feature.md` | путь к файлу | прочитать план как ТЗ (планы бэкенда — в `$BACKEND_REPO/plans/`) |
| Linear-задача | `ABC-123` или URL `linear.app/...` | прочитать задачу через Linear MCP как ТЗ — см. «Источники из MCP» |
| GitHub PR бэкенда | `#123`, `owner/repo#123` или URL PR | взять дифф PR через GitHub MCP как ТЗ — см. «Источники из MCP» |
| имя ветки бэкенда | не подошло ничему выше | взять `git -C "$BACKEND_REPO" diff main...<ветка>` как ТЗ; чекаута нет — сказать и попросить описание изменения или ссылку на PR |
| `METHOD /путь` (`POST /api/v1/ai/tailor`) | метод + путь | точечный прогон по одной ручке |

Аргумента нет — спросить, что покрываем. Не додумывать.

## Источники из MCP

Оркестратор выгружает данные из MCP **один раз, в файлы** — сабагенты MCP не видят
и работают только с файлами:

- **Linear-задача**: `mcp__linear__get_issue` + `mcp__linear__list_comments`
  (уточнения требований часто живут в комментариях) → сохранить
  в `.claude/tmp/<id>/requirements.md`. Читать как текст плана: ручки, формулы,
  границы, out of scope. ID задачи зафиксировать — он идёт в заголовок тест-плана
  и в описание MR.
- **GitHub PR**: сначала `mcp__github__pull_request_read` со списком файлов
  (пагинация 5–10, `minimal_output`), отфильтровать нерелевантное (миграции без
  API-эффекта, фронтенд, CI); затем дифф → `.claude/tmp/<id>/backend.diff`.
  Оттуда же — актуальная спека: `mcp__github__get_file_contents`
  (`path: docs/openapi.json`, `ref: <ветка PR>`) → `.claude/tmp/<id>/openapi.json`
  (playbook, шаг 1). Проектирование идёт по ней — поднятый стенд не нужен.
  В контекст оркестратора брать только заголовки файлов и хунки по затронутым
  ручкам; сабагентам передавать **путь** к файлу, не текст. Дифф PR равноценен
  локальному `git diff` во всех шагах playbook.
- **`owner/repo` бэкенда**: явная ссылка на PR в аргументе или Linear-задаче —
  оттуда; иначе из `git -C "$BACKEND_REPO" remote get-url origin`; иначе —
  `JLBegemot/cv-customs-webinar-version`. Репозиторий `cv-customs` — старый,
  не использовать.
- **Связка источников**: в аттачментах или описании Linear-задачи есть ссылка
  на PR — подтянуть и его; PR ссылается на задачу — подтянуть задачу. Есть только
  задача, без PR и без чекаута — работать по тексту задачи и контракту,
  как в ветке «чекаута нет».
- **MCP не подключён / нет прав / задача или PR не найдены** — сказать пользователю
  и попросить текст требований. Не падать и не додумывать.

## Что читать

1. `references/playbook.md` — процесс, шаги 0…8. Читать целиком до начала работы.
2. `references/profiles.md` — профили ручек (`http` / `sse` / `llm` / `job` / `ratelimit`):
   какая обвязка нужна и какие категории кейсов обязательны.
3. `docs/test-rules.md` — правила тестов. **Единственный источник**; не пересказывать
   их здесь и не выдумывать свои.

## Шаги

### Шаг 0. Режим

`full` или `delta` — **по фактам репозитория, а не по формулировке задачи**.
Подробности — playbook, шаг 0.

### Шаг 1. Требования

Прочитать источник из аргумента. Источник из MCP (Linear-задача, GitHub PR) —
сначала выгрузить в файлы по разделу «Источники из MCP». Выписать: затронутые
ручки, формулы, границы, out of scope. Чего в источнике нет — спросить,
не додумывать.

Иерархию правды MCP не меняет: текст Linear-задачи — уровень текста плана
(источник `[план]`), дифф PR — уровень кода хендлера (источник `[код]`);
стенд всё равно прав (playbook, шаг 0б).

### Шаг 2. Контракт и существующие тесты

Запустить сабагента `contract-explorer`. В промпт передать **пути и список ручек**,
не пересказ:

> Ручки: `<METHOD /path>`, … Контракт: `contracts/openapi.json`; актуальная спека
> из PR (если скачана): `.claude/tmp/<id>/openapi.json`. Тесты: `tests/`.
> Правила: `docs/test-rules.md`. Верни выжимку по формату из своего описания.

**Не читать `contracts/openapi.json` в этот контекст самому** — он на несколько тысяч
строк. Агента нет — сделать шаг самому, но читать спеку точечно:
`jq '.paths["/api/v1/ai/tailor"]' contracts/openapi.json`.

### Шаг 3. Пробелы и кейсы

По playbook, шаги 5 и 6. Определить пробелы (нет теста на сценарий или нет ассерта
на суть), спроектировать кейсы, **оба прохода дедупа**. Показать пользователю таблицей:
`TC-NNN`, ручка, что проверяем, приоритет, источник, статус.

### Шаг 4. Гейт  [СТОП]

Собрать **все** вопросы к пользователю одним блоком — до финализации плана.
Playbook, шаг 6б. Правила:

- сначала проверить репозиторий, потом спрашивать;
- дописывать вопросы к согласованному плану **запрещено**;
- без явного согласия дальше не идти.

После согласия записать:

- `plans/<id>-test-plan.md` — человекочитаемый план по формату шага 8;
- `.claude/tmp/<id>/cases.yaml` — исполняемое подмножество (только то, что идёт в код);
- проверить: `uv run python scripts/validate_cases.py .claude/tmp/<id>/cases.yaml`
  (ручки новые, в снапшоте их ещё нет — добавить
  `--spec .claude/tmp/<id>/openapi.json`).

### Шаг 5. Генерация

Прочитать `docs/test-rules.md`. Это первый шаг, где нужен стенд, — шаги 1–4 шли
по спеке из PR и снапшоту. Убедиться, что внешний стенд отвечает (поднимает
его пользователь, не пайплайн) и снапшот контракта синхронизирован с ним:

```bash
python scripts/openapi_snapshot.py --check   # заодно проверяет, что стенд отвечает
```

`--check` упал — контракт стенда уехал от снапшота; синхронизировать осознанно
(`--dump`) и сказать об этом в отчёте **до** генерации, иначе кейсы врут.

Писать можно только под `tests/`, `plans/`, `docs/` и `.claude/tmp/`. Конфигурацию
стенда пайплайн не трогает (FORBID-010): «подкрутить стенд, чтобы позеленело» —
то же нарушение, что правка прод-кода.

**До ~8 кейсов писать самому** — холодный старт сабагента дороже. От ~8 кейсов
и нескольких целевых файлов — запустить `test-writer`, по одному агенту на файл,
со своим диапазоном `TC`. Два агента не пишут в один файл.

### Шаг 6. Прогон и разбор

```bash
uv run pytest -q
```

Красный тест разбирается двумя вопросами по порядку (playbook, шаг 6 писателя):

1. Это стенд/окружение или код?
2. Это дефект сервиса или неверная предпосылка теста?

**Второй вопрос не решать самому** — вынести пользователю. Бэкенд в другом репозитории:
«позеленить» тест правкой хендлера физически нельзя, правка стенда под тест — то же
нарушение (FORBID-010).

### Шаг 7. Ревью

Запустить `test-reviewer` на изменённые файлы. Он возвращает находки списком
с severity и ID правила; **правки вносишь ты, в этом треде**. Максимум два круга.
Остались `blocker`-находки после второго — показать пользователю и остановиться.

### Шаг 8. Отгрузка

Вызвать `/ship`. Ветка `tests/<id>-<краткое-описание>`, описание MR по
`references/mr-comment.md` с таблицей кейсов из `cases.yaml`.

Источником была Linear-задача — после пуша предложить оставить в ней комментарий
со ссылкой на ветку/MR (`mcp__linear__save_comment`). Это внешнее действие:
только с явного подтверждения пользователя.

Снять маркер нужно и при **досрочной остановке** — на гейте шага 4, на blocker-находках
шага 7, по требованию пользователя.

## Незыблемые правила

- **Без утверждённого плана код не пишется.** Шаг 4 не пропускается и не делегируется.
- **Шаг 4 не автоматизируется никогда.** Согласование — единственное дешёвое место,
  где ловятся неверно понятые требования.
- **Правила — только из `docs/test-rules.md`.** Второй источник правил ломает всю
  конструкцию.
- **Стендом пайплайн не управляет.** Он поднят снаружи, его конфигурация меняется
  не отсюда и не под тест (STAND-001, FORBID-010).
- Скилл вызывается явно. Автозапуск восьмишагового пайплайна по фразе в чате не нужен.
