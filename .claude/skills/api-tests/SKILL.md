# Генерация API-тестов (чёрный ящик)

Оркестратор. Держит весь сценарий, потому что шаг 4 (гейт согласования) требует
диалога с пользователем, а сабагенты не разговаривают.

Тесты в этом репозитории — HTTP к поднятому стенду. Прод-код бэкенда живёт
в отдельном репозитории и здесь **не редактируется никогда**.

**Чекаут бэкенда** — справочный источник, путь берётся из переменной `BACKEND_REPO`.
Переменная пуста или путь не существует — чекаута нет: работать по контракту
и пробным запросам к стенду, помечая выводы `[инференс]`. Проверять так:

```bash
[ -n "$BACKEND_REPO" ] && [ -d "$BACKEND_REPO" ] && echo "чекаут есть: $BACKEND_REPO"
```

**Аргумент** — источник требований, любой из трёх:

| Вход | Что делать |
|---|---|
| `plans/NN-feature.md` | прочитать план как ТЗ (планы бэкенда — в `$BACKEND_REPO/plans/`) |
| имя ветки бэкенда | взять `git -C "$BACKEND_REPO" diff main...<ветка>` как ТЗ; чекаута нет — сказать и попросить описание изменения |
| `METHOD /путь` (`POST /api/v1/ai/tailor`) | точечный прогон по одной ручке |

Аргумента нет — спросить, что покрываем. Не додумывать.

## Что читать

1. `references/playbook.md` — процесс, шаги 0…8. Читать целиком до начала работы.
2. `references/profiles.md` — профили ручек (`http` / `sse` / `llm` / `job` / `ratelimit`):
   какая обвязка нужна и какие категории кейсов обязательны.
3. `docs/test-rules.md` — правила тестов. **Единственный источник**; не пересказывать
   их здесь и не выдумывать свои.

## Шаги

### Шаг 0. Режим

`full` или `delta` — **по фактам репозитория, а не по формулировке задачи**.
Подробности — playbook, шаг 0.

### Шаг 1. Требования

Прочитать источник из аргумента. Выписать: затронутые ручки, формулы, границы,
out of scope. Чего в источнике нет — спросить, не додумывать.

### Шаг 2. Контракт и существующие тесты

Запустить сабагента `contract-explorer`. В промпт передать **пути и список ручек**,
не пересказ:

> Ручки: `<METHOD /path>`, … Контракт: `contracts/openapi.json`. Тесты: `tests/`.
> Правила: `docs/test-rules.md`. Верни выжимку по формату из своего описания.

**Не читать `contracts/openapi.json` в этот контекст самому** — он на несколько тысяч
строк. Агента нет — сделать шаг самому, но читать спеку точечно:
`jq '.paths["/api/v1/ai/tailor"]' contracts/openapi.json`.

### Шаг 3. Пробелы и кейсы

По playbook, шаги 5 и 6. Определить пробелы (нет теста на сценарий или нет ассерта
на суть), спроектировать кейсы, **оба прохода дедупа**. Показать пользователю таблицей:
`TC-NNN`, ручка, что проверяем, приоритет, источник, статус.

### Шаг 4. Гейт  [СТОП]

Собрать **все** вопросы к пользователю одним блоком — до финализации плана.
Playbook, шаг 6б. Правила:

- сначала проверить репозиторий, потом спрашивать;
- дописывать вопросы к согласованному плану **запрещено**;
- без явного согласия дальше не идти.

После согласия записать:

- `plans/<id>-test-plan.md` — человекочитаемый план по формату шага 8;
- `.claude/tmp/<id>/cases.yaml` — исполняемое подмножество (только то, что идёт в код);
- проверить: `uv run python scripts/validate_cases.py .claude/tmp/<id>/cases.yaml`.

### Шаг 5. Генерация

Прочитать `docs/test-rules.md`. Убедиться, что внешний стенд отвечает (поднимает
его пользователь, не пайплайн) и снапшот контракта синхронизирован с ним:

```bash
python scripts/openapi_snapshot.py --check   # заодно проверяет, что стенд отвечает
```

`--check` упал — контракт стенда уехал от снапшота; синхронизировать осознанно
(`--dump`) и сказать об этом в отчёте **до** генерации, иначе кейсы врут.

Поднять маркер пайплайна:

```bash
touch .claude/tmp/api-tests-active
```

Пока он существует, хук `PreToolUse` запрещает запись вне `tests/`, `plans/`, `docs/`
и `.claude/tmp/` — в частности, любую правку `stand/.env.stand` (FORBID-011):
«подкрутить стенд, чтобы позеленело» становится невозможной случайно. Снять
маркер на шаге 8.

**До ~8 кейсов писать самому** — холодный старт сабагента дороже. От ~15 кейсов
и нескольких целевых файлов — запустить `test-writer`, по одному агенту на файл,
со своим диапазоном `TC`. Два агента не пишут в один файл.

### Шаг 6. Прогон и разбор

```bash
uv run pytest -q
```

Красный тест разбирается двумя вопросами по порядку (playbook, шаг 6 писателя):

1. Это стенд/окружение или код?
2. Это дефект сервиса или неверная предпосылка теста?

**Второй вопрос не решать самому** — вынести пользователю. Бэкенд в другом репозитории:
«позеленить» тест правкой хендлера физически нельзя, правка стенда под тест — то же
нарушение (FORBID-010, FORBID-011).

### Шаг 7. Ревью

Запустить `test-reviewer` на изменённые файлы. Он возвращает находки списком
с severity и ID правила; **правки вносишь ты, в этом треде**. Максимум два круга.
Остались `blocker`-находки после второго — показать пользователю и остановиться.

### Шаг 8. Отгрузка

Снять маркер пайплайна — иначе он будет мешать следующей задаче:

```bash
rm -f .claude/tmp/api-tests-active
```

Вызвать `/ship`. Ветка `tests/<id>-<краткое-описание>`, описание MR по
`references/mr-comment.md` с таблицей кейсов из `cases.yaml`.

Снять маркер нужно и при **досрочной остановке** — на гейте шага 4, на blocker-находках
шага 7, по требованию пользователя.

## Незыблемые правила

- **Без утверждённого плана код не пишется.** Шаг 4 не пропускается и не делегируется.
- **Шаг 4 не автоматизируется никогда.** Согласование — единственное дешёвое место,
  где ловятся неверно понятые требования.
- **Правила — только из `docs/test-rules.md`.** Второй источник правил ломает всю
  конструкцию.
- **Стендом пайплайн не управляет.** Он поднят снаружи; `stand/.env.stand` — только
  справка об ожидаемом профиле, её смена — отдельный MR (STAND-001, FORBID-011).
- Скилл вызывается явно. Автозапуск восьмишагового пайплайна по фразе в чате не нужен.
